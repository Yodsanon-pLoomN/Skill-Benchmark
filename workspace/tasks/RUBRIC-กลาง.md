## กติกาการเขียน checklist item (ใช้ตอนเขียน `checklist.md` ของแต่ละ task)

1. **ตอบได้จาก diff/response อย่างเดียว** — ห้ามเขียนคำถามที่ต้องรันโค้ดจริงหรือดูอะไรนอกเหนือจากผลงานที่ส่งมา (sandbox ไม่มี network รัน test จริงไม่ได้)
2. **1 ข้อ = 1 ข้อเท็จจริงที่ตรวจสอบได้ (yes/no)** — ไม่ใช่คำถามรวม ("โค้ดดีไหม") ต้องเจาะจง ("ฟังก์ชัน X เพิ่ม null check ก่อนเรียก Y หรือไม่")
3. **ไม่มีคะแนนบางส่วนในข้อเดียว** — ข้อนั้นผ่านหรือไม่ผ่านเท่านั้น ถ้าอยากวัดความละเอียด ให้แตกเป็นหลายข้อย่อยแทน
4. **ดึงมาจาก `NOTES.md` ของ task นั้น** (เฉลย/worked example ที่มีอยู่แล้ว) — ไม่ให้ grader หรือกระบวนการอัตโนมัติเป็นคนคิดคำถามเอง เพื่อไม่ให้ผู้ตรวจกับผู้ออกโจทย์เป็นกระบวนการเดียวกัน
5. **ไม่ยกคะแนนให้ test ที่เพิ่มเองโดยอัตโนมัติ** — เว้นแต่ test นั้นผิด (นับเป็นข้อไม่ผ่านในหมวดคุณภาพ) ตามธรรมเนียมเดิม
6. **แยกข้อ "ความถูกต้อง/ความครบถ้วน" กับข้อ "คุณภาพ" ให้เห็นชัดในไฟล์** (คงโครงจาก worked example เดิมที่มีอยู่แล้วใน NOTES.md ทุก task) แต่**ไม่แยกให้คะแนนเป็นด้าน ๆ อีกต่อไป** — ทุกข้อรวมกันเป็น checklist เดียวของ run นั้น (สำหรับ task ที่ไม่มีโค้ด เช่น explain-01 ให้ตีความหมวดคุณภาพเป็น "คุณภาพของคำอธิบาย" เหมือนเดิม)

## เกณฑ์ตัดสินระดับ run

- Run นั้น**ผ่าน** ถ้า **≥80%** ของ checklist item ทั้งหมด (ของ task นั้น) ได้คะแนนสุดท้ายเป็นผ่าน
- ต่ำกว่านั้น = **ไม่ผ่าน**
- ไม่มีถ่วงน้ำหนักข้อสำคัญ/ไม่สำคัญ ทุกข้อนับเท่ากัน (กันการตัดสินใจแบบอัตวิสัยเรื่อง weight)

## กติกาการตรวจ (blind + ตรวจซ้ำ 3 รอบ)

- **Blind** — grader เห็นแค่เนื้อหา diff/response ที่ `generate_report.py` สลับลำดับซ่อน label แล้ว ไม่รู้ว่า run นั้นมาจากเงื่อนไข off หรือ skill ไม่รู้ run_code/session_id
- **ตรวจ 3 รอบอิสระต่อ run (pass 1-3)** — orchestrator เดียว (`run-skill-batch.sh` ที่ `/skill-benchmark` เรียก) ยิง `claude -p` แยกกัน 3 ครั้งต่อ checklist เดียวกัน แต่ละรอบไม่เห็นคำตอบของรอบอื่น
  - คะแนนสุดท้ายของแต่ละข้อ = **เสียงข้างมาก (2 ใน 3)** ไม่มีการยิงรอบที่ 4 (3 รอบไม่มีทางเสมอกัน)
  - **เหตุผลที่ใช้ 3 รอบ ไม่ใช่ 2:** วรรณกรรมสาย LLM-as-judge ยืนยันตรงกัน 2 งาน ว่า AI judge รอบเดียว/สองรอบไม่นิ่งพอเชื่อถือได้ — Haldar & Hockenmaier, *Rating Roulette: Self-Inconsistency in LLM-As-A-Judge Frameworks* (EMNLP 2025, arXiv:2510.27106) วัด agreement ข้ามรอบด้วย Krippendorff's Alpha พบว่าต่ำกว่าเกณฑ์ยอมรับได้ (0.8) ในหลายกรณี และเสนอ majority voting ข้าม ≥3 รอบอิสระ; Norman, Rivera, & Hughes, *Reliability without Validity* (arXiv:2606.19544) กำหนด Minimum Viable Validation Protocol ไว้ตรง ๆ ว่า "**≥3 independent runs**"
  - **ไม่บังคับ temperature=0** สำหรับการตรวจ (ใช้ sampling ปกติของ `claude -p` เหมือน task-running call) — จริง ๆ แล้ว**ไม่มีทางเลือกให้บังคับ** เพราะ Claude Sonnet 5 ไม่รับพารามิเตอร์ `temperature` ผ่าน `claude -p` อยู่แล้ว (ดู `วิธีการวัด-Token-และต้นทุน.md` ข้อ 6.4) แต่บังเอิญตรงกับข้อเสนอของ Rating Roulette ที่พบว่าการบังคับ deterministic (temp=0) กลับทำให้ agreement กับคนแย่ลง แม้จะดูนิ่งกว่าบนกระดาษ (ขัดกับ MVVP ของ Reliability without Validity ที่แนะนำ temp=0 — วรรณกรรม 2 งานนี้ขัดกันเอง แต่ในทางปฏิบัติไม่กระทบ เพราะกำหนด temperature ไม่ได้อยู่ดี)
- **ข้อจำกัดที่ต้องเขียนรับ:** ตรวจซ้ำนิ่ง (reliability) ไม่เท่ากับตัดสินถูก (validity) — ถ้าทั้ง 3 รอบเข้าใจผิดจุดเดิมซ้ำกัน (bias ร่วม) วิธีนี้จับไม่ได้ ไม่มีคนตรวจคู่ขนานอีกต่อไปหลังเปลี่ยนวิธี (ดู เอกสารอ้างอิงฯ หัวข้อ 4.7)
- **ไม่วัด token/cost ของการตรวจเอง** — ตัดสินใจไว้ชัดเจน (21 ส.ค. 2569) ไม่ instrument `grade_runs.py` ด้วย `extract_tokens.py` ต้นทุนตรวจจึงไม่มีตัวเลขอ้างอิงได้ ต้องเขียนรับเป็นข้อจำกัดในบทที่ 5 ไม่ใช่ความบกพร่องที่ลืมทำ

## กติกาทั่วไป (สืบทอดจาก rubric เดิม)

- ตัดสินจาก**ผลงานที่ส่งมาเท่านั้น** (diff หรือคำอธิบาย) ห้ามอนุมานว่าใครทำ/เครื่องมือไหนทำ
- ไม่มี test suite รันให้ดู (sandbox ไม่มี network) — ห้ามตัดสินว่าไม่ผ่านเพราะไม่มีผลรัน test ตัดสินจากโค้ด/เนื้อหาที่เขียนจริง
- คำอธิบายที่ยาวขึ้นไม่ได้แปลว่าผ่านง่ายขึ้น ตัดสินจากเนื้อหาที่ถูกต้อง/ครบถ้วนเท่านั้น

## สิ่งที่ต้องมีต่อ task

แต่ละ task ยังต้องมี:
- `prompt.txt` — โจทย์คงที่
- `NOTES.md` — เฉลย/สิ่งที่ต้องถูกสำหรับ task นั้น (ไม่ให้ grader เห็น)
- `base.tag` — สภาพโค้ดตั้งต้น
- **`checklist.md`** (ใหม่) — รายการคำถาม yes/no เจาะจงต่อ task ตามกติกาข้างบน แทนที่ rubric 0-4 เดิม
