ฉันอ่านไฟล์ฝั่ง frontend ทั้งสามไฟล์แล้ว แต่ยังอ่านโค้ด backend (`sample-project`) ไม่ได้ เพราะสิทธิ์อ่านโฟลเดอร์นั้นยังไม่ได้รับ ส่วนที่บอกว่า backend ส่งอะไรกลับมาจึงมาจาก interface และคอมเมนต์ใน frontend ไม่ได้มาจากการอ่านกฎใน `docs/DOMAIN.md` ฉันไม่ได้แก้ไฟล์ใดเลย

## 1. หน้าที่ของ RoomService กับ RoomAvailabilityComponent

**`RoomService`** (`room.service.ts`) เป็นชั้นเรียก HTTP บางๆ ไปยัง Node API
- มี 2 method: `listRooms()` เรียก `GET /rooms` และ `getAvailability(roomId, date)` เรียก `GET /rooms/:id/availability?date=...`
- ประกาศ type ของข้อมูลที่ API ส่งกลับ ได้แก่ `Room`, `FreeInterval` (`startsAt` / `endsAt` เป็น string) และ `AvailabilityResponse`
- คอมเมนต์ในไฟล์บอกชัดว่า service ไม่ implement กฎธุรกิจเอง เป็นแค่ท่อส่งข้อมูล backend คือแหล่งความจริงของกฎการจอง
- คืนค่าเป็น `Observable` และไม่เก็บ state เอง

**`RoomAvailabilityComponent`** ดูแล state ของหน้าจอและการแสดงผล
- เก็บ state ไว้ 6 ตัว: `rooms`, `selectedRoomId`, `date`, `freeIntervals`, `loading`, `errorMessage`
- สั่งให้ service โหลดข้อมูลเมื่อหน้าโหลดหรือเมื่อผู้ใช้เปลี่ยนห้อง/วันที่
- แปลงช่วงเวลาเป็นข้อความที่แสดงผ่าน `formatSlot`

**ทั้งสองคุยกันอย่างไร:** component รับ `RoomService` ผ่าน constructor injection (service เป็น `providedIn: 'root'` จึงเป็น singleton) แล้ว `subscribe` ผลลัพธ์เอง ฝั่ง service ไม่รู้จัก component เลย ทิศทางพึ่งพาจึงเป็นทางเดียว

## 2. ลำดับตั้งแต่โหลดหน้าจนเห็นช่วงเวลาว่าง

1. `ngOnInit` ตั้ง `date` เป็นวันนี้ด้วย `new Date().toISOString().slice(0, 10)` ได้สตริง `YYYY-MM-DD`
2. เรียก `listRooms()` ถ้าสำเร็จ จะเก็บผลลง `rooms` แล้วเลือกห้องแรกเป็น `selectedRoomId`
3. ถ้ามีห้องอย่างน้อย 1 ห้อง จะเรียก `loadAvailability()` ต่อทันที ถ้าไม่มีห้องเลย จะไม่โหลดอะไรและหน้าจอว่างโดยไม่มีข้อความแจ้ง ถ้าโหลดห้องพลาด จะแสดง "Could not load rooms."
4. `loadAvailability()` จะไม่ทำอะไรถ้าห้องหรือวันที่ว่าง เมื่อผ่านเงื่อนไขแล้วจะตั้ง `loading = true` ล้าง `errorMessage` แล้วเรียก `getAvailability(selectedRoomId, date)`
5. backend ตอบ `AvailabilityResponse` ในรูป `{ roomId, date, free: [{ startsAt, endsAt }, ...] }` ตาม interface ฝั่ง frontend ค่าที่ใส่ใน `free` คือช่วงเวลาที่ว่างจริง ซึ่ง backend คำนวณมาให้แล้ว (หักการจองที่มีอยู่ออกแล้ว) frontend ไม่คำนวณเพิ่ม
6. `next` handler ทำแค่ `this.freeIntervals = res.free` แล้วตั้ง `loading = false` ถ้า error จะแสดง "Could not load availability."
7. template วนลูป `*ngFor` ผ่าน `freeIntervals` และเรียก `formatSlot(slot)` ต่อแต่ละช่วง
8. `formatSlot` สร้าง `Date` จากสตริงทั้งสองฝั่ง ตัดเป็น `HH:mm` ด้วย `toISOString().slice(11, 16)` แล้วต่อเป็น `"09:00–10:00 UTC"`
9. ถ้า `freeIntervals` ว่าง จะแสดง "No free slots."

เมื่อผู้ใช้เปลี่ยน select หรือ date input ตัว `(ngModelChange)` จะเรียก `loadAvailability()` ซ้ำ เริ่มจากข้อ 4

## 3. จุดที่ต้องระวังเรื่อง half-open interval `[start, end)`

ความหมายคือ `startsAt` นับรวม ส่วน `endsAt` ไม่นับรวม ช่วงว่าง 09:00–10:00 จึงหมายถึงเวลา 10:00 พอดีไม่ได้อยู่ในช่วงนี้ และช่วง 09:00–10:00 กับ 10:00–11:00 ต่อกันได้พอดีโดยไม่ทับกัน

ตอนนี้โค้ดปลอดภัยเพราะไม่ได้เปรียบเทียบหรือรวมช่วงเลย (ตามคอมเมนต์บรรทัด 55–57) ถ้าจะเขียนเพิ่ม ต้องระวังตามจุดเหล่านี้:

- **`formatSlot` (บรรทัด 58–63)** ตัวเลขท้ายใน `09:00–10:00` คือขอบที่ไม่นับรวม ถ้าไปแก้ให้ดูเหมือนนับรวม เช่นลบ 1 นาทีให้เป็น `09:59` หรือบวกเพิ่ม ผู้ใช้จะเข้าใจผิดว่า 10:00 ยังว่างอยู่หรือถูกใช้ไปแล้ว
- **ช่วงสุดท้ายของวัน** ถ้า backend ตัดวันที่ 24:00 UTC ค่า `endsAt` จะเป็นเที่ยงคืนของวันถัดไป `formatSlot` จะแสดงเป็น `22:00–00:00 UTC` ซึ่งอ่านเหมือนเวลาเริ่มวัน แม้ตามหลัก half-open จะถูกต้องก็ตาม
- **การตัดเป็น `HH:mm`** การ `slice(11, 16)` ทิ้งวินาทีและมิลลิวินาที ถ้า backend ส่ง `endsAt` ที่ไม่ได้ปัดเป็นนาทีพอดี ป้ายจะแสดงเวลาที่ไม่ตรงกับขอบจริง
- **โค้ดใหม่ที่จะเปรียบเทียบ รวม หรือกรองช่วงฝั่ง client** เช่น ซ่อนช่วงที่สั้นกว่า 30 นาที รวมช่วงที่ติดกัน หรือเช็คว่าเวลาที่ผู้ใช้เลือกอยู่ในช่วงไหม ต้องใช้ `start <= t && t < end` เท่านั้น ถ้าเขียน `t <= end` หรือถือว่าช่วงที่ต่อกันพอดีเป็นการทับซ้อน ผลที่ได้จะต่างจาก backend
- **ความยาวช่วง** คำนวณด้วย `end - start` ได้ตรงๆ ใน half-open ห้ามบวก 1 เหมือนช่วงแบบนับรวมปลายทั้งสองด้าน

ผู้ใช้จะเห็นคำตอบผิดได้แม้ backend ถูกต้อง เช่น ช่วงว่างที่ต่อกัน 09:00–10:00 และ 10:00–11:00 ถูกโค้ด client มองว่าทับกันแล้วตัดทิ้ง หรือป้ายเวลาถูกเลื่อนจนผู้ใช้จองชนกับเวลาที่ถูกจองไปแล้ว

## ข้อสังเกตเพิ่มเติมที่ไม่เกี่ยวกับ half-open แต่ควรรู้

- **วันที่ใช้ UTC:** `toISOString()` ให้วันที่ตาม UTC ไม่ใช่เวลาท้องถิ่น ผู้ใช้ในไทย (UTC+7) ที่เปิดหน้าช่วงก่อน 07:00 จะได้วันที่เมื่อวานเป็นค่าเริ่มต้น และป้ายเวลาทั้งหมดแสดงเป็น UTC ซึ่งอาจทำให้ผู้ใช้อ่านเวลาคลาดเคลื่อน 7 ชั่วโมง
- **ไม่มีการยกเลิก request เดิม:** ถ้าผู้ใช้เปลี่ยนห้องหรือวันที่เร็วๆ หลายครั้ง คำตอบของ request เก่าที่ช้ากว่าอาจมาทับผลของ request ใหม่ได้ ทำให้หน้าจอแสดงข้อมูลของห้องหรือวันที่ไม่ตรงกับที่เลือกอยู่ การแก้ปกติคือใช้ `switchMap` หรือยกเลิก subscription เดิม
- **ข้อความ error ทั่วไป:** ทั้งสองจุดไม่แยกสาเหตุ (เครือข่ายล่ม, 4xx, 5xx) ผู้ใช้เห็นข้อความเดียวเหมือนกันหมด

ถ้าอยากให้ยืนยันรูปแบบ response จริงและกฎ half-open ฝั่ง backend ให้อนุญาตให้ฉันอ่าน `workspace/sample-project` (โดยเฉพาะ `docs/DOMAIN.md` และ `checkAvailability`) แล้วฉันจะกลับมาเทียบกับข้อ 2 และ 3 ให้
